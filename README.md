# Садовый реестр

Веб-приложение для систематизированного учёта садовых участков. Оно объединяет сведения об участках, их владельцах и платежах, показывает сводные показатели и помогает быстро находить нужные записи.

## Назначение

Садовый реестр переводит учёт из разрозненных файлов и консольных операций в единый браузерный интерфейс. Данные представлены в реляционном виде: участок связан с владельцем, платёж — с плательщиком. На страницах приложения можно просматривать эти связи и агрегированные результаты SQL-запросов.

## Возможности

- **Сводка реестра** — количество участков, владельцев и платежей, общая задолженность.
- **Поиск участков** — поиск по номеру участка или имени владельца.
- **Фильтрация участков** — отбор свободных, занятых, арендованных и спорных участков.
- **Карточка участка** — площадь, статус, долг, дата регистрации и контактные данные закреплённого владельца.
- **Реестр владельцев** — контактные сведения, число связанных участков и сумма долга.
- **История платежей** — дата, назначение, сумма и имя владельца.
- **Статистика** — распределение участков по статусам, средняя площадь и список владельцев с задолженностью.
- **Обработка пустых результатов** — интерфейс сообщает, когда по выбранному условию записей нет; неизвестные адреса ведут на страницу 404.

Веб-интерфейс предназначен для просмотра и анализа данных. Исходная консольная версия `main.py` сохранена как предыдущий этап проекта.

## Разделы приложения

| Адрес | Содержание |
| --- | --- |
| `/` | Сводные показатели и навигация |
| `/registry/plots/` | Реестр участков, поиск и фильтры |
| `/registry/plots/<id>/` | Подробная карточка участка |
| `/registry/owners/` | Список владельцев и агрегаты по участкам |
| `/registry/payments/` | История платежей с именами плательщиков |
| `/registry/statistics/` | Сводная аналитика по реестру |
| `/admin/` | Стандартная административная панель Django |

## Данные и связи

| Таблица | Содержание | Связи |
| --- | --- | --- |
| `owners` | ФИО, телефон, почта, дата создания записи | Один владелец может быть связан с несколькими участками и платежами |
| `plots` | Номер, площадь, статус, владелец, задолженность | `owner_id` ссылается на `owners.id`; для свободного участка владелец не обязателен |
| `payments` | Владелец, сумма, дата и назначение платежа | `owner_id` ссылается на `owners.id` |

Для базы данных предусмотрены SQLite- и PostgreSQL-схемы. Ограничения проверяют уникальность номера участка, допустимые статусы, положительную площадь и сумму платежа, а внешние ключи сохраняют целостность связей.

Публикуемая версия работает с PostgreSQL через `DATABASE_URL`. JSON-файлы из исходного проекта не публикуются, поскольку содержат личные данные. Для первичного наполнения предусмотрен обезличенный демонстрационный набор из `fixtures/`; команда `setup_registry` создаёт таблицы и импортирует доступные записи.

## Как устроена обработка данных

1. Маршрут Django передаёт HTTP-запрос в представление нужного раздела.
2. Представление получает параметры поиска или фильтра и вызывает SQL-функцию.
3. Параметризованный запрос выполняется в PostgreSQL либо SQLite; для связанных сведений используются `JOIN`.
4. Результат преобразуется в строки с именованными столбцами и передаётся Django-шаблону.
5. Шаблон отображает список, карточку или агрегатную статистику.

Таблицы предметной области обслуживаются SQL напрямую, без Django ORM. В `sql/queries.sql` собраны запросы для списков, фильтрации `WHERE`, соединений `JOIN`, подсчёта и суммирования, группировки `GROUP BY`, условий `HAVING`, поиска с параметрами и пагинации. Представления используют выборки из этого слоя в рабочих страницах приложения.

## Структура проекта

- `garden_site/` — настройки, корневая маршрутизация и точки запуска Django.
- `home/` — обзорная страница.
- `registry/` — представления, маршруты, SQL-выборки и шаблоны реестров.
- `templates/` — базовый шаблон, общая навигация и страница 404.
- `static/` — таблица стилей и скрипт интерфейса.
- `db/` — подключение к выбранной базе и импорт JSON.
- `sql/` — схема SQLite, схема PostgreSQL и примеры запросов.
- `fixtures/` — обезличенные примеры для демонстрации.
- `models/`, `services/`, `storage/`, `cli/` — сохранённая консольная реализация проекта.

## Публикация на Render

Проект рассчитан на Render Web Service: Django формирует страницы на сервере и подключается к PostgreSQL. GitHub Pages подходит для статических HTML/CSS/JavaScript-сайтов и не запускает Django-приложение.

В настройках сервиса Render задаются переменные окружения:

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL URL из Neon или Render PostgreSQL. Вставляйте URL, начинающийся с `postgres://` или `postgresql://`; если копируете команду `psql '…'`, приложение удалит оболочку автоматически. Сам пароль не добавляйте в репозиторий. |
| `DJANGO_SECRET_KEY` | Длинная случайная строка, созданная отдельно для Render |
| `DJANGO_ALLOWED_HOSTS` | `.onrender.com` или имя собственного домена; Render hostname также определяется автоматически |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | HTTPS-адрес собственного домена, если он используется |

Команда запуска сервиса:

```bash
python manage.py migrate --noinput && python manage.py setup_registry && python manage.py collectstatic --noinput && gunicorn garden_site.wsgi:application
```

Та же конфигурация указана в `render.yaml`. При использовании **Blueprint** выберите этот файл; при создании **Web Service** задайте команду выше в поле **Start Command**. После развёртывания откройте адрес Render и проверьте страницы из таблицы разделов.

Подробности о формате соединения и Django на Render: [руководство Render](https://render.com/docs/deploy-django). GitHub Pages работает как статический хостинг: [документация GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).
