# Садовый реестр

Веб-приложение для систематизированного учёта садовых участков. Оно объединяет сведения об участках, их владельцах, платежах и аренде, показывает сводные показатели и помогает быстро находить нужные записи.

## Назначение

Садовый реестр переводит учёт из разрозненных файлов и консольных операций в единый браузерный интерфейс. Данные хранятся в реляционной базе: участок связан с владельцем, платёж — с плательщиком, аренда — с участком и арендатором. Доступ к данным выполняется средствами Django ORM, поэтому структура базы описывается моделями и миграциями, а представления работают с объектами, а не с SQL-строками.

## Возможности

- **Сводка реестра** — количество участков, владельцев и действующих аренд, общая задолженность.
- **Реестр участков** — поиск по номеру или владельцу, фильтр по статусу, сортировка, постраничный вывод.
- **Карточка участка** — площадь, статус, долг, членский взнос, изображение, владелец, история аренды и последние платежи.
- **Реестр владельцев** — контакты, число участков, сумма оплат и задолженности.
- **Платежи** — поиск, фильтр по состоянию, сортировка и постраничный вывод.
- **Аренда участков** — список с фильтрами, карточка аренды; действующая аренда блокирует участок, отменённая — нет.
- **Формы создания и редактирования** — участки, владельцы, платежи и аренда оформляются через Django Forms с серверной проверкой данных и загрузкой изображения.
- **Отмена вместо удаления** — платёж и аренда переводятся в состояние «отменён»: запись остаётся в истории и не влияет на расчёты и занятость участка.
- **Статистика** — распределение участков по статусам, средняя площадь, задолженность по владельцам, статусы аренды.
- **Обработка пустых результатов и ошибок** — интерфейс сообщает об отсутствии записей, неизвестные адреса ведут на страницу 404.

Консольная версия `main.py` сохранена как первый этап проекта.

## Модели Django

| Модель | Таблица | Поля | Связи |
| --- | --- | --- | --- |
| `Owner` | `registry_owner` | ФИО, телефон, почта, даты создания и изменения | Один владелец — много участков, платежей и аренд |
| `Plot` | `registry_plot` | Номер, slug, площадь, статус, задолженность, изображение, членский взнос | `owner` → `Owner`, `on_delete=SET_NULL`, `related_name="plots"` |
| `Payment` | `registry_payment` | Сумма, дата, назначение, состояние | `owner` → `Owner`, `on_delete=PROTECT`, `related_name="payments"` |
| `Lease` | `registry_lease` | Даты начала и окончания, статус, арендная плата, комментарий | `plot` → `Plot` (`CASCADE`), `owner` → `Owner` (`PROTECT`), `related_name="leases"` |

Особенности реализации:

- `TimeStampedModel` — абстрактная модель с полями `created_at` и `updated_at`, от неё наследуются все сущности.
- `TextChoices` — статусы участка (`free`, `occupied`, `leased`, `disputed`), аренды (`active`, `cancelled`, `completed`) и платежа (`posted`, `cancelled`).
- Ограничения БД: положительная площадь, неотрицательный долг, корректный период аренды.
- `Plot.membership_fee` — вычисляемое `GeneratedField`: база сама хранит площадь × 12 ₽/м².
- `Plot.slug` формируется из номера участка с транслитерацией (`16-Б` → `16-b`) и используется в адресе карточки.
- Валидаторы `validate_plot_number` и `validate_phone` проверяют формат данных на уровне модели и формы.
- Менеджеры и QuerySet-методы: `Plot.objects.free()`, `Plot.objects.search()`, `Lease.objects.active()`, `Lease.objects.overlapping()`, `Payment.objects.posted()`.

## Слой данных: Django ORM

Доступ к данным сосредоточен в `registry/queries.py`:

- `plot_page()` — фильтрация, поиск, сортировка и пагинация списка участков с `select_related("owner")`;
- `owner_page()` — `annotate()` с `Count` и `Sum` для числа участков, оплат и долга;
- `payment_page()`, `lease_page()` — фильтры по состоянию, датам и сортировка;
- `available_plots()` — участки без действующей аренды на выбранный период;
- `dashboard_stats()` и `statistics()` — `aggregate()` и группировка `values().annotate()`.

Представления получают готовые объекты и передают их в шаблоны, поэтому SQL-запросов в `views.py` нет.

## Административная панель

Панель `Django Admin` настроена для всех моделей (`registry/admin.py`):

| Модель | Список | Поиск и фильтры | Связанные записи |
| --- | --- | --- | --- |
| Владельцы | ФИО, телефон, почта, число участков, долг | поиск по ФИО, телефону и почте; фильтр по дате и статусу участков | встроенные таблицы участков, аренд и платежей |
| Участки | номер, статус, площадь, владелец, долг, взнос, число аренд, миниатюра | поиск по номеру, slug и владельцу; фильтр по статусу, владельцу и дате | встроенная таблица аренды участка |
| Платежи | дата, владелец, сумма, назначение, состояние | поиск по владельцу и назначению; фильтр по состоянию и дате | автодополнение владельца |
| Аренда | участок, арендатор, период, длительность, плата, статус | поиск по участку и арендатору; фильтр по статусу | автодополнение участка и владельца |

Возможности административной панели:

- `list_display`, `list_filter`, `search_fields`, `ordering`, `list_per_page`, `date_hierarchy` — навигация по данным.
- `list_editable` — задолженность участка меняется прямо в списке.
- `autocomplete_fields` — выбор владельца и участка по подсказке вместо длинного списка.
- `inlines` — аренды и платежи видны в карточке владельца и участка.
- Действия (`actions`): освободить участки, перевести в спорные, обнулить долг, начислить пеню 5 % через `F()`, отменить платежи и аренды.
- Отмена платежа и аренды меняет статус записи, а не удаляет её: история сохраняется.

## Формы Django

Формы описаны в `registry/forms.py`, шаблоны — в `registry/templates/registry/form_page.html` и `includes/filter_form.html`.

| Форма | Базовый класс | Назначение и проверки |
| --- | --- | --- |
| `PlotFilterForm` | `forms.Form` | поиск, статус, сортировка, минимальная площадь; проверяет длину строки поиска и числовые значения |
| `OwnerFilterForm` | `forms.Form` | поиск владельца по ФИО, телефону и почте |
| `PaymentFilterForm` | `forms.Form` | поиск, состояние, сортировка и период; проверяет порядок дат |
| `LeaseFilterForm` | `forms.Form` | участок, арендатор, статус, период и сортировка |
| `PlotForm` | `ModelForm` | номер, площадь, статус, владелец, долг, изображение; проверяет формат номера, площадь, согласованность статуса и владельца, размер файла |
| `OwnerForm` | `ModelForm` | ФИО, телефон, почта; проверяет формат телефона |
| `PaymentForm` | `ModelForm` | владелец, сумма, дата, назначение; запрещает будущую дату и нулевую сумму, подставляет текущую дату |
| `LeaseForm` | `ModelForm` | участок, арендатор, период, плата; запрещает прошедшую дату начала, обратный период и пересечение с действующей арендой, при редактировании исключает саму запись |

Как устроена обработка:

1. Фильтры передаются GET-запросом, форма проверяет параметры и отдаёт `cleaned_data` в слой запросов. Некорректные значения не приводят к ошибке: показывается предупреждение и список без фильтра.
2. Создание и редактирование выполняются POST-запросом с `{% csrf_token %}`, после успешного сохранения — перенаправление (PRG), сообщение и повторное открытие формы с ошибками при неудаче.
3. `LeaseForm` проверяет доступность участка через `Lease.objects.active()` и `exclude(pk=self.instance.pk)`; `PlotForm.clean()` не даёт сохранить свободный участок с владельцем и занятый участок без владельца.
4. Загрузка изображения: `enctype="multipart/form-data"`, `request.FILES`, `ImageField(upload_to="plots/")`, файлы сохраняются в `media/plots/` и отдаются Django в режиме разработки.
5. Отмена платежа и аренды выполняется только POST-запросом (`@require_POST`); GET возвращает 405, а статус записи меняется через методы модели `cancel()`.



## Отладка запросов

При `DJANGO_DEBUG=1` подключается Django Debug Toolbar: панель `SQL` показывает запросы страницы, время выполнения и дубликаты. Настройки вынесены в `garden_site/settings.py` и `garden_site/urls.py`, в рабочем режиме панель отключена. Контекстный процессор `registry.context_processors.registry_summary` добавляет в подвал счётчики реестра.

## Переход с SQL-слоя ПР7

Стратегия перехода — новая структура таблиц (`registry_*`) и перенос существующих данных:

1. `sql/schema.sql` (SQLite) и `sql/schema_postgres.sql` (PostgreSQL) описывают таблицы ПР7.
2. Команда `python manage.py legacy_sql_import` создаёт эти таблицы и заполняет их данными из JSON — это предыдущий слой проекта.
3. Миграция `registry.0002_transfer_legacy_sql_data` читает `owners`, `plots`, `payments` и создаёт записи моделей с сохранением идентификаторов и внешних ключей; на чистой базе шаг пропускается.
4. Все дальнейшие изменения структуры выполняются только миграциями Django.

## Запуск локально

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate

pip install -r requirements.txt
python manage.py migrate
python manage.py setup_registry       # демонстрационные данные через ORM
python manage.py createsuperuser      # доступ к /admin/
python manage.py runserver
```

Файлы `sql/*.sql`, `db/database.py` и `db/import_json.py` сохранены как реализация ПР7. При необходимости её можно воспроизвести командой `python manage.py legacy_sql_import` на отдельной базе.

## Структура проекта

- `garden_site/` — настройки, корневая маршрутизация, точки запуска.
- `home/` — обзорная страница.
- `registry/` — модели, миграции, ORM-запросы, формы, сервисы, представления, административная панель и шаблоны.
- `registry/tests/` — тесты моделей, запросов, представлений, форм и административной панели.
- `reports/` — отчёты по практическим работам: `PR9_Django_ORM_modeli_otchet.docx`, `PR10_Django_ORM_Admin_otchet.docx`, `PR11_Django_Forms_otchet.docx`, скриншоты в `reports/screenshots/` и скрипт сборки отчётов.
- `templates/` — базовый шаблон, навигация, пагинация и страница 404.
- `static/` — таблица стилей и скрипт интерфейса.
- `sql/`, `db/` — предыдущий SQL-слой ПР7 (схемы, импорт JSON, работа с соединением).
- `fixtures/` — обезличенный демонстрационный набор.
- `models/`, `services/`, `storage/`, `cli/` — консольная версия проекта.

## Публикация на Render

Проект рассчитан на Render Web Service: Django формирует страницы на сервере и подключается к PostgreSQL.

Команда запуска сервиса:

```bash
python manage.py migrate --noinput && python manage.py setup_registry && python manage.py collectstatic --noinput && gunicorn garden_site.wsgi:application
```

Та же конфигурация указана в `render.yaml`. Подробности о формате соединения и Django на Render: [руководство Render](https://render.com/docs/deploy-django).
